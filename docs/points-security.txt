积分安全修复与上线说明（2026-10-21）

代码基线：839c3c2（已包含单人兑换上限）；修复分支：fix/points-security-invariants。

修复内容

1. 提现退款：WithdrawalRefund 用提现单的一对一约束防重。退款、来源批次、流水及状态在同一事务内写入；重复查询和并发查询最多退款一次。退款和付款均校验原提现的完整扣款流水及金额，不能只依据 approved 状态或一个可空的 transaction 外键。退款保留原扣款批次的有效期。
2. 资料完善奖励：外部贡献查询完成后锁定用户，重新检查状态、资料、身份和领取资格，条件更新领取标志并原子入账。ProfileRewardIdentity 以 provider+uid 唯一约束保留已领取身份，解绑、换绑、账号删除不能清掉身份资格记录。
3. 账号合并：按用户 ID 顺序锁定双方，与奖励发放共用锁；传播已领奖状态，保留身份记录；阻止在合并后向已停用源账号发奖。
4. 后台发放：用户和组织发放视图、操作按钮统一要求 points.grant_points 权限；is_staff 或其他模型权限不再代表有权发放积分。
5. 结果未知付款：请求超时、响应解析或签名异常保留扣款，进入 UNKNOWN 并继续按已保存批次/商户单号查询。不自动重发或退款，直到查询得到明确终态。商户单号按提现 ID 稳定生成。
6. 提现状态：Admin 的状态及审核人/时间只读；受控审核操作负责扣款。手工完成操作不能绕过扣款或抢先完成已进入自动付款的申请。
7. 付款幂等：在数据库事务内锁定并预占提现单，PaymentRecord.withdrawal_request 有唯一约束，网络请求放在预占提交之后。终态处理同时锁定提现单与付款记录，拒绝重放/降级和跨批次、空订单号匹配。PaymentRecord Admin 禁止新增、修改和删除，避免破坏防重证据。
8. 有效期：PointSource.objects.available() 统一用于可用余额、消费、兑换、提现及分配入口。分配按实际 FIFO 来源逐批保留金额、标签和有效期，包括待领取与领取入账；同一接收者可能对应多条来源。
9. 触达奖励：保留资金池标签，以实际扣款流水的互不重叠区间为接收者分配奖励来源。原来源已过期的份额不发放，其余份额保留原有效期；没有真实扣款证据或超出奖励池时拒绝发奖。这里遵循已有“标签积分不能无规则转换为通用积分”的领域规则。

补充加固

- 有加密业务数据却没有签名的身边云响应直接拒绝。
- 付款使用提现申请中冻结的收款信息，不读取之后可能被编辑的 WithdrawalAccount。
- 调度器使用到期自动释放的租约，不做非原子的 get/delete 提前释放，避免旧任务删掉新任务的锁；资金正确性依赖数据库约束。
- 兑换服务测试固定无折扣贡献数据，避免外部/缓存贡献结果干扰原价账本断言。等级折扣本身继续由独立测试覆盖。

上线步骤

1. 暂停旧版本付款/查询调度器，并在维护窗口部署，避免新旧代码混跑。
2. 核查同一提现对应多条 PaymentRecord 的历史记录。shenbianyun.0003 在建唯一约束前检查重复；如存在会明确报错并停止，不会删除或自动合并历史付款。需要结合平台真实流水人工处理后再迁移。
3. 运行 uv run manage.py migrate。包含 points.0009、accounts.0020 和 shenbianyun.0003 三项迁移。
   - 已有退款来源回填唯一退款事件，不重新发放或扣回积分。
   - 已有领奖标志/来源回填稳定身份记录，沿已有 merged_into 链传播领取标志。
4. 向被授权的后台人员/组显式授予 points.grant_points；不自动向全部 staff 授权。超级管理员保持权限。
5. 确认新版本及迁移在所有服务实例生效后恢复调度器，检查 UNKNOWN、异常状态冲突及历史退款/付款对账。

兼容性与历史边界

- 启用有效期后，过去已过期但仍有 remaining_amount 的来源不再计入可用余额；不删除历史来源和流水。
- 之前已发成“永久积分”或“无标签积分”的记录，本次不会推断归属后批量改账。需要根据历史分配/触达流水另行核对。
- 已解绑且没有历史身份关联证据的旧奖励，无法仅从当前绑定表恢复原 provider+uid；迁移保留所有可从现有领奖、绑定及合并记录确定的资格。
- 旧代码已标记 FAILED 并退款的实际成功付款，不会自动改成成功或再扣款，需要人工对账。
- 付款结果长期未知时保留待核对状态；不凭“查询不到”就认定失败并退款。
- 触达奖励扣款对账失败时记录活动与接收记录 ID，跳过该笔发奖，单条和批量标记已读继续执行。异常奖励保持未领取、未过期状态；修复扣款证据后可重试领取，仍受原领取期限和幂等约束限制。
- 分配者仍可在自己或自己有管理权限的组织资金池内指定接收者及金额；这项业务权限不代表只能按贡献排名自动发放。若产品要强制限定贡献名单，需要另行定义服务端筛选与分配政策。
- 支付平台使用本地 stub 验证协议分支，没有对真实付款服务发起交易；上线仍需要检查真实平台的结果查询字段。

测试入口

- points.tests.test_security_regressions：原审计漏洞的拒绝/幂等回归，及权限、元数据、历史状态、失败回滚等边界。
- points.tests.test_security_concurrency：独立数据库连接并发验证奖励、退款、付款任务、分配及跨商品兑换；SQLite 跳过，PostgreSQL 必须实际执行。
- points.tests.test_security_migrations：验证历史领取/退款回填及历史重复付款阻止迁移且保留证据。
- shenbianyun.tests：签名、客户端和租约回归。
- shop.tests.test_redemption_limits：单人兑换上限与真实并发回归。
- 完整验收使用 just test，包含浏览器 E2E 和项目覆盖率门禁。
